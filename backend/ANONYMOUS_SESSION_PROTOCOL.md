# Anonymous installation session protocol — proposal

**Status:** design proposal only; not implemented or deployed.  
**Protocol version:** 1  
**Scope:** Android installation enrollment, short-lived access sessions, proof of possession, revocation and rotation.

This document turns the anonymous-session requirements in `backend/README.md` and `SECURITY.md` into a reviewable protocol. It does not authorize the Android client to use a placeholder endpoint or imply that a backend exists.

## Security goals

- No Microsoft/Cortana account or user-facing login.
- Anonymous does not mean unauthenticated: each installation proves possession of a generated private key.
- Provider credentials remain exclusively on the backend.
- Access credentials are short-lived, scoped and revocable.
- Enrollment challenges and request proofs are single-use to limit replay.
- Session identity is not derived from IMEI, phone number, advertising ID or other hardware identifiers.
- Logs never contain private keys, access tokens, full authorization headers or message bodies by default.

## Cryptographic profile

- Installation signing key: ECDSA P-256 (`secp256r1`) generated by Android Keystore on API 23+.
- Signature: SHA-256 with ECDSA (`SHA256withECDSA`).
- Public key transport: JWK with `kty=EC`, `crv=P-256`, and base64url-encoded `x` and `y`; private key is never exported.
- Hashes: SHA-256, base64url without padding.
- Transport: HTTPS only; authenticated endpoints reject redirects.
- Challenge nonce: at least 256 bits from a cryptographically secure random generator.
- Access token: opaque, cryptographically random, short-lived; store only a hash server-side.

The API 23+ key-storage gate is intentional. API 19–22 must not silently fall back to a plaintext or hard-coded key. Any lower-API session strategy requires a separate security review and explicit product decision.

## Enrollment flow

### 1. Request a one-time challenge

`POST /v1/enrollment/challenges`

Request:

```json
{
  "protocolVersion": 1,
  "purpose": "enroll"
}
```

Response:

```json
{
  "protocolVersion": 1,
  "challengeId": "opaque-random-id",
  "nonce": "base64url-32-byte-or-longer-random-value",
  "expiresInSeconds": 120
}
```

Server requirements:

- Challenge expires after 120 seconds.
- Challenge is bound to its intended purpose (`enroll` or `rotate`); enrollment requests explicitly set `purpose: "enroll"`. Rotation challenges require an active session and valid proof of possession for that session.
- Challenge can be consumed once only, using an atomic state transition.
- Apply IP/network abuse limits without requiring a stable user identity.

### 2. Generate installation key and sign challenge

The Android client creates a non-exportable P-256 signing key pair in Android Keystore. It calculates the public-key thumbprint and signs this exact UTF-8 message (LF line endings, no trailing LF):

```text
CORTANAGPT-ENROLL-V1
{challengeId}
{nonce}
{publicKeyThumbprint}
```

The thumbprint is SHA-256 over the RFC 7638 canonical JWK member serialization for P-256: `{"crv":"P-256","kty":"EC","x":"...","y":"..."}`.

### 3. Complete enrollment

`POST /v1/sessions`

This endpoint is only for first-time enrollment. Rotation uses the separate authenticated flow below.

Request:

```json
{
  "protocolVersion": 1,
  "challengeId": "same-challenge-id",
  "publicKey": {
    "kty": "EC",
    "crv": "P-256",
    "x": "base64url-coordinate",
    "y": "base64url-coordinate"
  },
  "publicKeyThumbprint": "base64url-sha256-thumbprint",
  "signature": "base64url-DER-ECDSA-signature"
}
```

The server validates the JWK and thumbprint, then atomically consumes the matching unexpired, unused enrollment challenge **before signature verification**. It verifies the ECDSA signature against the returned nonce and submitted key. A challenge is burned even when signature verification fails; clients must request a fresh challenge rather than retrying a failed proof.

Response:

```json
{
  "protocolVersion": 1,
  "sessionId": "opaque-session-id",
  "accessToken": "opaque-random-secret",
  "tokenType": "CortanaPoP",
  "expiresInSeconds": 900,
  "serverTime": "RFC3339-UTC-timestamp",
  "scopes": ["chat:send", "session:revoke"]
}
```

Recommended initial access-token lifetime: 15 minutes. The token is bound server-side to the installation public-key thumbprint. Never return a refresh token; renew by completing a fresh signed challenge.

## Proof of possession for authenticated requests

Every authenticated request includes:

- `Authorization: CortanaPoP {accessToken}`
- `X-Cortana-Proof: {base64url-DER-ECDSA-signature}`
- `X-Cortana-Timestamp: {UNIX-TIMESTAMP-SECONDS}` (decimal seconds, no leading zeroes)
- `X-Cortana-Proof-ID: {unique-proof-jti}` (16–128 base64url characters, generated afresh for every HTTP attempt)
- A client-generated unique `X-Request-ID` for chat requests.

The timestamp and proof ID headers are mandatory. Their exact byte-for-byte values are included in the signed canonical message below. Header names are case-insensitive as required by HTTP; header values are not normalized. Reject duplicate instances of any security-sensitive header rather than choosing one.

The CortanaPoP signature covers this exact UTF-8 canonical message (LF line endings, no trailing LF):

```text
CORTANAGPT-POP-V1
{HTTP-METHOD-UPPERCASE}
{PATH-AND-QUERY}
{SHA256-OF-EXACT-REQUEST-BODY-BASE64URL}
{UNIX-TIMESTAMP-SECONDS}
{unique-proof-jti}
{SHA256-OF-ACCESS-TOKEN-BASE64URL}
```

Server requirements:

- Verify the signature against the public key bound to the session.
- Enforce a small clock-skew window (recommended ±60 seconds).
- Atomically reject a repeated proof `jti` for the same key within the replay-retention window (recommended at least 5 minutes).
- Verify the body hash over the exact received bytes, before parsing.
- Reject malformed, oversized, expired, revoked or wrong-scope requests.
- Do not redirect authenticated requests.

This is a project-specific detached-signature proof format. It is **not RFC 9449 DPoP**, does not use the standardized DPoP JWT format, and must not be advertised as interoperable with RFC 9449. The `CortanaPoP` authorization scheme and `X-Cortana-Proof` header are proposal-only names pending independent protocol review.

## Chat request and durable idempotency

`POST /v1/chat/completions`

The JSON body follows the version-1 proposal in `docs/ARCHITECTURE.md`. Server-side idempotency key is the tuple:

`(sessionId, requestId)`

The backend must persist the request state and response so retries cannot trigger a second billable model call. Reusing the same request ID with a different normalized body hash must return a conflict, not execute a new turn. The response `requestId` must equal the client request ID.

The server must enforce request-size, selected-memory-size, output-token and rate limits before unbounded allocation or provider execution.

## Renewal, rotation and revocation

### Authenticated rotation flow

Rotation must not be confused with first-time enrollment or accept an unauthenticated challenge purpose.

1. The client requests a rotation challenge using `POST /v1/enrollment/challenges` with `purpose: "rotate"`, the current `sessionId`, the current access token and a valid CortanaPoP proof over that request.
2. The server verifies that the session is active and the current key proof is valid, then issues a short-lived challenge bound to that session and purpose.
3. The client signs the challenge using the already-bound installation private key and submits it to `POST /v1/sessions/rotate` with the session ID, challenge ID, public-key thumbprint and signature.
4. The server verifies the signature, confirms the submitted public key is the key already bound to the session, atomically consumes the challenge, issues a new token and revokes the previous token in one transaction.

Rotation does not silently replace a lost installation key. A separate reviewed key-recovery protocol would be required for that.

- **Renewal:** a successful authenticated rotation issues a new access token and revokes the previous token atomically.
- **Key loss:** if the private key is unavailable, the old session cannot be renewed. The client starts a new enrollment; the old session expires naturally or is revoked through an available recovery mechanism. Do not invent a device identifier as a recovery secret.
- **Revocation:** `DELETE /v1/sessions/current` requires a valid access token and CortanaPoP proof. Revoke the session and all its tokens server-side.
- **Local logout:** clear token preferences and delete the local Keystore key. The existing probe's `destroy()` method is intended to provide this local destruction behavior.

## Error contract

Use stable machine-readable error codes, without stack traces or provider details. Initial codes:

- `CHALLENGE_EXPIRED`
- `CHALLENGE_ALREADY_USED`
- `INVALID_PROOF`
- `SESSION_EXPIRED`
- `SESSION_REVOKED`
- `PROOF_REPLAYED`
- `INSUFFICIENT_SCOPE`
- `IDEMPOTENCY_CONFLICT`
- `REQUEST_TOO_LARGE`
- `RATE_LIMITED`

Responses should include a correlation ID that is safe to expose; do not echo secrets or sensitive request content.

## Operational controls

- Persist challenge consumption, session state and idempotency records transactionally.
- Store only a one-way hash of access tokens.
- Encrypt sensitive server-side data at rest and restrict access to signing/provider secrets.
- Redact authorization headers, CortanaPoP proof values, private-key material and message content from logs.
- Set explicit retention limits for challenges, replay IDs, idempotency records and operational metadata.
- Apply per-IP, per-key and per-session quotas; anonymous enrollment must not become unlimited free provider access.
- Provider errors are normalized; internal stack traces and provider credentials never reach clients.

## Acceptance tests before implementation is considered complete

1. Valid enrollment proof creates one session bound to the submitted key.
2. Invalid signature, wrong thumbprint, expired challenge and reused challenge are rejected.
3. Replaying a valid CortanaPoP proof is rejected.
4. A proof signed by a different key cannot use the session token.
5. Expired/revoked tokens and insufficient scopes are rejected.
6. Renewal rotates tokens and revokes the old token atomically.
7. Repeated `(sessionId, requestId)` with identical body returns the stored result without a second provider call.
8. Reusing a request ID with a different body returns `IDEMPOTENCY_CONFLICT`.
9. Revocation prevents subsequent requests.
10. Logs and error responses contain no access token, private key, authorization header or provider secret.

## Explicit non-claims

- No endpoint in this document is live.
- Repository-level backend primitives and CI exist, but no public endpoint, production authentication boundary, provider adapter, deployment or production secret configuration exists yet.
- The protocol has not undergone an independent cryptographic/security review.
- Android API 19–22 enrollment behavior is intentionally unresolved and must not be enabled by a silent insecure fallback.


### Current server-side verifier boundary (not a public route)

The backend now contains `server/src/security/authenticated-request.ts`, a route-independent pipeline that:

1. Strictly parses the `CortanaPoP {token}` authorization value and the proof, timestamp and proof-ID headers.
2. Resolves the token to an active session using the session-token repository.
3. validates the stored P-256 public JWK and compares its RFC 7638 thumbprint to the session binding.
4. Verifies the signature over the exact method, origin-form target, raw body, timestamp, proof ID and token hash.
5. Atomically claims the proof ID in Redis for 300 seconds.
6. Enforces the route's required session scope.

The helper accepts injected session and replay interfaces so the ordering and fail-closed outcomes can be unit-tested. Redis/database failures throw and must be converted to a generic server error at the HTTP boundary. This helper is still proposal-only, not wired to Fastify, and not independently reviewed. The HTTP adapter must capture raw bytes before JSON parsing, reject duplicate security headers, and derive the origin-form target from the trusted request object—not from forwarded headers.
